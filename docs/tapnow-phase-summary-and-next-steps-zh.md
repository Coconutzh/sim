# TapNow 改造阶段总结与下一步计划

本文档用于同步当前基于 `sim` 做 TapNow 向二次开发的阶段进度，说明已经完成的工作、当前状态、已知风险，以及下一步建议执行顺序。

## 一、当前目标

本阶段的目标不是一次性重写整个平台，而是在尽量少动底层执行引擎、实时协作协议、工作流持久化能力的前提下，先从原始 `sim` 中抽出一个更接近 TapNow 使用方式的最小可用内核：

- 画布编辑可用
- Agent 节点可用
- Copilot 改图可用
- 工作流运行与调试可用
- 多人协作可用
- 长尾第三方能力先裁剪，避免界面和认知负担过重

## 三、当前状态判断

### 1. 产品代码侧

当前代码状态已经从“原始全量 sim 平台”推进到“TapNow 向 MVP 内核”的阶段，至少在方向上已经完成了第一轮真正落地，而不是停留在方案讨论。

可以认为以下几件事已经成立：

- 核心编辑器、执行器、协作和 Copilot 没有被拆坏
- 长尾集成已经开始被真正削减
- 可见能力面已经开始收缩
- 后续改造可以在当前分支基础上继续推进

### 2. 工程与环境侧

本地环境文档已经补齐，但环境本身仍然存在一个现实前提：

- 如果使用原生 Windows PostgreSQL，必须额外解决 `pgvector` 安装问题

也就是说，当前源码开发不再缺文档，但数据库层仍然依赖开发者机器是否具备可用的 `vector` 扩展。

### 3. 验收侧

当前最大缺口不是“还没做更多代码”，而是：

- 还没有完成一轮完整的人工联调验收

也就是还没有严格按照下面这条链路做一次端到端实操确认：

- 建图
- 改图
- 运行
- 调试
- 协作

这一步做完，才能判断第一阶段是否真的可作为团队继续开发的稳定基线。

## 四、当前已知风险

### 1. `pgvector` 仍然是 Windows 原生开发的主要门槛

如果团队里很多开发者都使用 Windows 原生 PostgreSQL，那么最容易卡住的点不是代码，而是：

- `CREATE EXTENSION vector` 无法成功
- `bun run db:migrate` 因为缺少 `vector` 扩展失败

这会直接影响知识库相关能力和完整迁移。

### 2. 当前阶段更偏“能力收口”，还不是最终产品体验重构

虽然第一阶段已经把产品面往 TapNow 方向推了一大步，但当前更多完成的是：

- 剪掉不需要的能力
- 限制能力暴露面
- 保住核心执行链

还没有深入到真正的 TapNow 级交互重塑，例如：

- 节点交互复杂度进一步下降
- 画布默认路径更短
- 新手空白态与引导体验优化
- 改图反馈路径和心智模型继续收敛

### 3. 还需要一轮真实使用视角的清单化验收

如果只看代码和文档，阶段一已经够继续推进；但如果按最终产品验收口径，还需要通过一次真实跑通来确认：

- 是否还有漏网的复杂入口
- Copilot 是否会生成不希望暴露的能力
- 画布上常用创建路径是否足够短
- 协作过程是否稳定

## 五、下一步建议怎么干

建议不要再大面积盲目删东西，而是按下面顺序推进。

### 第一步：先完成一轮人工联调验收

这是当前最重要的下一步。

验收目标：

- 在本地环境中完整跑通 `建图 -> 改图 -> 运行 -> 调试 -> 协作`

建议检查点：

- 新建工作流是否顺畅
- 画布块选择是否已明显收敛到 MVP 白名单
- Agent 节点是否可正常配置和执行
- Copilot 是否能增删改节点，且不会继续引入非目标能力
- 执行日志、暂停、恢复、报错提示是否可用
- 两个浏览器窗口下的实时协作是否正常同步

这一步完成后，建议把结果再单独沉淀成一份“人工验收报告”。

### 第二步：根据验收结果修复核心链路问题

人工联调后，如果发现问题，优先级建议如下：

1. 阻断主流程的问题  
   例如无法建图、无法运行、无法协作、Copilot 无法改图

2. 明显破坏 TapNow 简洁体验的问题  
   例如入口太深、默认选择太多、仍然暴露复杂长尾能力

3. 可以后续再做的次级体验问题  
   例如样式、提示文案、边缘操作不够顺手

### 第三步：继续收缩剩余非核心能力面

在人工验收确认主链路没问题后，再继续推进下一批裁剪。

建议原则：

- 优先裁剪纯工具集成面
- 暂缓裁剪牵涉 webhook、外部入口、消息触发器、产品外层能力面的高风险集成
- 每一批继续保持“先盘点引用，再物理删除，再补文档，再提交”的节奏

### 第四步：进入真正的 TapNow 体验重构

当 MVP 内核稳定后，下一阶段才适合把重点切到“像 TapNow 一样好上手但又足够强大”的产品体验改造。

建议聚焦：

- 画布默认创建路径简化
- 常用块的默认模板化
- Agent 操作路径缩短
- Copilot 改图反馈更加直接
- 首次使用的空白态与引导设计
- 调试面板的信息组织方式

### 第五步：标准化团队本地开发方案

如果后续多人并行开发，建议尽快统一团队的本地环境标准，不要让每个人各自踩一次 Windows + pgvector 的坑。

建议二选一：

- 团队统一使用 Docker 版 Postgres + pgvector
- 或者团队统一沉淀一套 Windows 原生 pgvector 安装方案

否则后面会反复消耗在环境问题上。

## 六、建议的近期执行顺序

建议按下面的顺序推进最近几步：

1. 先把本地环境彻底跑通，确保 `3000` 和 `3002` 都能稳定起来
2. 完成一次人工联调验收
3. 记录验收问题并修复阻断项
4. 在主链路稳定后继续做下一批裁剪
5. 开始真正的 TapNow 交互与体验重构

截至当前，这个项目的 TapNow 向改造已经不再是“想法阶段”，而是已经完成了第一轮真实落地：

- 仓库核心结构已经梳理清楚
- 核心能力白名单已经明确
- 部分长尾集成已经被物理移除
- 核心产品面已经开始按 MVP 白名单收口
- 本地开发部署文档已经补齐
- 开发环境中的几个主要启动阻塞已经被处理

下一步最关键的不是继续无差别删代码，而是先做一轮真实人工联调，把当前阶段基线验稳。验收稳住之后，再进入下一轮裁剪和体验重构，整体推进会更稳，也更接近最终要复现的 TapNow 产品目标。
